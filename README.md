# InterMap

친구(이웃)들이 다녀온 맛집을 지도 위에 올려 보는 서비스. 제품 정의는 [PRODUCT.md](PRODUCT.md), 모바일 앱 빌드는 [docs/mobile-app-guide.md](docs/mobile-app-guide.md).

- `frontend/` — React 19 + Vite + TypeScript, Naver Map. Vercel 배포, Capacitor로 iOS/Android 패키징.
- `backend/` — Spring Boot. Render 배포, DB는 Neon Postgres (로컬은 H2 파일).

이 문서는 **성능 개선 기록**이다. 무엇이 느렸고, 왜 그 방식으로 풀었는지, 다음에 규모가 커지면 어디를 건드려야 하는지를 남긴다.

---

## 성능 설계 원칙

1. **DOM 마커는 200개를 넘기지 않는다.** Naver Map 마커는 DOM 요소다. 모바일 WebView에서 마커가 200개를 넘으면 지도를 살짝만 밀어도 화면 전체가 다시 그려지며 깜빡인다. 마커를 빠르게 그리는 게 아니라 마커 수 자체를 줄이는 쪽으로 설계한다.
2. **데이터는 보이는 만큼만 받는다.** 가게는 수천~수만 건이다. 전체를 한 번에 받지 않고 지도가 멈출 때 보이는 영역만 받아 누적한다.
3. **입력은 즉시, 무거운 계산은 뒤로.** 검색어 입력처럼 사용자가 타이핑하는 경로는 `useDeferredValue`로 필터·재군집을 뒤로 미룬다.
4. **바뀐 것만 다시 만든다.** 배열·객체를 새로 만들면 그 아래 메모와 마커가 전부 재생성된다. 변화가 없으면 이전 참조를 그대로 돌려준다.

## 적용된 개선

### 1. 데이터 로딩

#### 뷰포트 단위 로딩 + 누적 (`2fd4b34`, 2026-08-28)
- 전에는 앱 시작 시 `/api/restaurants` 전체를 받았다. 가게가 수천 건이 되자 첫 화면이 수 초 걸렸다.
- 지도 이동이 멈추면(`idle`) 보이는 영역(여유 포함)의 bbox만 요청하고, 받은 가게는 클라이언트 목록에 누적한다. 한 번 본 영역의 가게는 남는다.
- 서버 응답에 `Cache-Control: max-age=6h, public`. 가게 데이터는 주 2회 배치 동기화로만 바뀌므로 충분하다.
- 코드: `App.tsx` `loadViewport`, `RestaurantController.list`

#### 낮은 줌 요약 셀 (`33aeff8`, 2026-08-28)
- 줌 15 이하에서는 화면에 수천 개 가게가 들어온다. 개별 가게 대신 **격자 셀 요약**(대표 좌표 + 건수)만 받는다. `/api/restaurants/summary`.
- 셀 한 변 = 프론트 군집 반경(26px)을 해당 줌의 경도 단위로 환산한 값. 서버와 프론트가 같은 격자를 쓴다.
- 요청은 `zoom - 1`로 보내 셀 한 변을 2배(52px)로 키운다. 셀 수가 1/4로 줄어 밀집 지역에서도 마커가 수백 개를 넘지 않는다.
- 코드: `RestaurantController.summary`, `App.tsx` `loadViewport` 셀 모드 분기

#### bbox 격자 스냅 (`33aeff8`)
- bbox를 그대로 URL에 넣으면 조금만 움직여도 URL이 바뀌어 6시간 HTTP 캐시가 한 번도 맞지 않는다.
- bbox를 0.02도 격자에 스냅해 같은 타일이면 같은 URL이 되게 했다. 직전과 같은 요청 키면 요청 자체를 건너뛴다(`lastFetchKey`).
- 코드: `App.tsx` `snapBBox`

#### 요약 셀 누적 (`98559b9`, 2026-08-28)
- 요약 셀을 응답마다 통째로 갈아끼우면 응답이 오기 전까지 마커가 사라져 이동할 때마다 깜빡였다.
- 서버와 같은 격자 인덱스를 키로 누적한다. 같은 셀은 최신 응답으로 덮어써서 bbox 경계에 걸려 잘렸던 건수도 교정된다. 줌이 바뀌면 격자가 달라지므로 그때만 비운다.
- 코드: `App.tsx` `cellStore`

#### 병합 비용 (`33aeff8`)
- `mergeRecords`: 이동마다 수천 건이 들어오므로 매 건 `find`로 훑지 않고 이름+주소 Map으로 찾는다. 달라진 게 없으면 **이전 배열을 그대로 반환**해 아래쪽 메모(재군집·마커 재생성)가 돌지 않게 한다.

#### DB 인덱스
- `restaurant(lat, lng)` 복합 인덱스. bbox 조회와 요약 집계가 이걸 탄다.

### 2. 후기·사진 (`622a3d1`, 2026-08-31)

- 후기 목록은 작성자를 join fetch로 한 번에 가져온다 (후기마다 사용자 조회하는 N+1 방지).
- 목록 응답에는 사진 **id만** 싣는다. 바이트는 `/api/photos/{id}`로 따로 받고 `Cache-Control: max-age=1y, immutable` — 사진은 올라간 뒤 바뀌지 않는다.
- 업로드 전에 프론트에서 **1280px JPEG로 축소**한다(`lib/image.ts`). 원본 수 MB → 수백 KB. 서버 요청 상한은 장당 5MB, 10장.
- 후기 목록은 로그인한 사용자에게만 받는다. 로그아웃하면 비운다.

### 3. 마커 렌더링 (`MapCanvas.tsx`, `lib/cluster.ts`)

#### 군집화 (`770d269` 2026-08-26 → `33aeff8`)
- 화면 픽셀 거리 기준 그리디 군집화. 처음엔 O(n²)였고 "핀 수백 개까지는 충분"이라고 표시해 두었다가, 뷰포트 로딩으로 수천 건이 들어오자 **격자 버킷 3×3 이웃 비교**로 바꿨다. 거리 ≤ 셀 한 변이면 반드시 이웃 셀 안에 있으므로 결과는 전수 비교와 동일하다.
- 줌 21 미만은 군집 반경 50px, 최대 줌에서만 26px. 넓게 볼 때 마커 수를 더 줄인다.

#### 뷰포트 밖 마커 생성 안 함 (`af8ad45`, 2026-08-26)
- 화면(여유 35%) 밖의 핀은 마커 DOM을 만들지 않는다. 데이터가 수백 건을 넘으면 화면 밖 마커가 지도 이동을 끊기게 만든다.
- 재군집·마커 갱신은 이동이 끝난 뒤(`idle`) 한 번만. 애니메이션 도중에 재군집하면 마커가 갈리며 화면이 움찔거린다.

#### 히스테리시스 (`3f109f2`, 2026-08-28)
- 조금 움직일 때마다 경계 마커를 지웠다 만들면 모바일 WebView에서 마커 전체가 깜빡였다.
- 직전 뷰포트(여유 포함)가 아직 화면을 다 덮고 줌도 같으면 마커를 갱신하지 않는다.
- 모바일 핀치는 소수점 줌으로 멈춘다. 그대로 쓰면 idle마다 군집이 달라지므로 정수로 반올림해 판단한다.

#### 그리기 비용
- 줌 15 미만에서는 핀 이름 라벨을 숨긴다 (`221abe0`). 빽빽할 때 텍스트 페인트가 비싸다.
- 선택 강조(포커스 링)는 바뀐 핀의 아이콘만 다시 그린다. 전체 마커 재생성 없음.
- 마커는 군집 key로 Map에 캐시하고 diff한다. 같은 key면 그대로 두고, 없어진 것만 지우고 새 것만 만든다.

### 4. React 렌더 파이프라인

- `useDeferredValue(query)`: 검색어 입력은 즉시 반영하고 필터·재군집은 뒤로 미룬다.
- `reviewedRestaurants`: 후기 없는 가게는 객체를 그대로 두고 후기 있는 가게만 새 객체로 만든다. 그래야 마커 diff가 대부분 "변화 없음"으로 끝난다.
- `cellList`: 셀 Map이 바뀔 때만 배열을 다시 만든다.
- 그룹 색은 CSS 변수(`--gc-*`) 하나로 내려보낸다. 색을 바꿔도 마커·시트·칩이 리렌더 없이 따라온다.

### 5. 검색 (2026-09-01)

- **2글자 입력 시점 1,132ms → 110ms** (가게 5,000건 로드 상태, Chrome Long Task 측정).
  - 원인: 검색 결과 목록을 열지 말지는 동기값(`query`)으로 판단했는데, 목록 내용은 지연값(`deferredQuery`) 기준이었다. 2글자가 되는 프레임에 지연값은 아직 1글자(키워드 없음)라 **필터 전 가게 전체를 행으로 동기 렌더**한 뒤, 다음 패스에서 진짜 결과로 다시 그렸다.
  - 수정: 목록 표시 여부도 지연값 기준으로. 결과 목록은 50행 상한(지도에는 전부 찍힘). 남은 110ms는 5,000건 필터와 마커 갱신.
- 가게 이름 검색은 서버에도 물어본다(`/api/restaurants?q=`, 상한 50건). 클라이언트에 없는 영역의 가게도 걸린다.
- 검색 중·"후기 있음" 필터일 때는 결과 수가 적으므로 줌과 무관하게 개별 핀을 그린다. 요약 셀은 숨긴다.

## 측정 방법

- **Long Task**: Playwright로 페이지를 열고 `PerformanceObserver({ entryTypes: ['longtask'] })`를 심은 뒤 사용자 동작을 재현한다. 50ms 넘는 메인 스레드 작업이 잡힌다.
- **CPU 프로파일**: `page.context().newCDPSession(page)` → `Profiler.start/stop`. 함수별 self/total 시간을 합산하면 어느 컴포넌트가 무거운지 바로 보인다.
- 백엔드 없이 재현하려면 `page.route('**/api/**')`로 응답을 흉내낸다. 가게 5,000건·셀 300개 정도면 실제 규모의 병목이 나온다.
